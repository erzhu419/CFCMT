**可以继续解决，而且这个项目值得推进。但你贴出的下一步建议还需要改一层：不能直接再做一个“regret-aligned gate”，因为仓库已经试过相近路线；真正需要先解决的是——有用的 source 和有利的动作，能否根据部署时实际可获得的信息被识别出来。**

我核查了这个分支的实验检查点、V144/V148 协议、论文讨论，以及部分动作排序和门控代码。以下是基于这些材料的诊断与实施方案，**不是已经完成的代码修复或重新运行的 SUMO 结果**。

## 一、仓库中有三个重要信息，会改变下一步方向

### 1. 并不是完全没有 source 收益，而是“事后能找到，事前还选不稳”

你提供的摘要没有突出 V144：记录显示，在七个目标城市中，**每个城市都存在至少一个事后表现有用的 source**；42 个有向 source–target 组合中，约 59.5% 改善 target-only，但平均效果只有 `−0.00037944`。这比“所有 source 都没有价值”更值得研究。

不过，V144 明确属于 **descriptive oracle inventory**：它看过目标评估结果后寻找最优 source，不能作为部署策略，也没有证明这些最优 source 在新的随机实现中仍然有效。

所以当前应当区分：

> **存在事后收益 → 收益能在新数据中重复 → 能用事前信息识别 → 能转化为长期闭环收益。**

目前第一步有证据，后面三步不能直接跳过去。

### 2. “直接按下游收益选择 source”不是尚未尝试的新方向

V142 已经直接在 source-null、单 source 和 uniform-source 的不同权重之间，按下游策略表现选择；它仍然失败，最终退回 source-null。V140 也不是优化器不会给 source 分配权重，而是非零权重随后被验证门槛否决。

代码层面，`source_gated_pairwise.py` 也已经存在 **city-out-of-fold 的 `cost_delta` 学习，以及误差分位数构造的门控余量**。它选择的是 rigid/pairwise expert，而非完全等同于你拟议的 source gate，但足以说明：“预测收益差，再加保守门控”这个思想在项目中并不新。

**因此，下一轮必须明确改变迁移对象、状态表示或监督信息，不能只换一个损失函数名称。**

### 3. 压力控制器的瓶颈也不只是“缺少一个保守回退”

检查点记录了更强的反差：V125 的事后 pressure-nondegrading oracle 存在明显收益，但学习出来的 held-out guard 略有伤害；V130–V135 又陆续检验了改善分类、优势回归、广义压力规则、历史查表和机制代理，仍未形成稳定的部署收益。

这意味着，**“有好动作”与“控制器能提前辨认好动作”之间，确实存在瓶颈**。但 oracle 本身可能挑中了部分随机有利结果，因此还要进一步判断：瓶颈来自缺少信息，还是来自标签噪声、模型能力或数据量。

## 二、核心科研问题：先做“收益可辨识性”诊断，再开发新 gate

我建议把下一轮的第一个目标写成：

> **在当前可观测状态和信息预算下，source 的增量收益是否具有可预测、可重复的条件结构？**

这比直接问“哪个 source 更好”更具体，也能决定后续资源应该投在哪里。

### 第一项诊断：V144 的 source 排名能否重复？

不需要重新做一遍相同 oracle inventory，而应当在**现有七城的新增开发数据**上检验：

用一部分开发种子确定 source 的排序或选择规则，然后在另一部分未参与选择的种子上固定评估。重点不是再次报告“每个城市的最佳 source”，而是看：

**先前选出的 source 是否继续有益、收益符号是否稳定、是否只在某些交通状态下有益。**

这能区分两种完全不同的问题：

| 诊断结果                        | 意味着什么                  | 下一步                  |
| --------------------------- | ---------------------- | -------------------- |
| source 排名或条件收益较稳定，但 gate 选错 | 可利用信号存在，选择方法不足         | 改进低复杂度的条件 utility 模型 |
| 排名频繁翻转，但加入特定状态信息后稳定         | 当前表示把不同机制混在一起          | 改表示，再学迁移             |
| 固定条件下的平均收益仍接近零、噪声很大         | 事后 headroom 可能主要来自随机波动 | 改采样与监督，不继续堆 gate     |

这批新增数据仍是**开发数据**，不能因为种子是新的，就把它们称为新方法的独立城市确认。

### 第二项诊断：把“状态不同”与“未来随机性不同”分开

目前不同种子之间的收益反转，可能同时包含状态分布变化和未来随机变化。建议在七城开发环境中增加小规模、明确隔离的配对诊断：

**固定同一个决策检查点和同一个可执行动作，重复采样合理的未来随机实现，比较条件平均收益，而不是只看某一次 rollout 的收益。**

例如，对于一个固定的 source 候选：

$$
U_s(x)
=
\mathbb E\!\left[
C_H(x,a_{\mathrm{TO}})
-
C_H(x,a_s)
\mid x
\right].
$$

这里，\(a_{\mathrm{TO}}\) 是 target-only 选择的动作，\(a_s\) 是加入 source 后的动作，\(C_H\) 是预先规定的后续控制协议下的成本。

要估计的是这个**条件期望差**，而不是：

$$
\text{某一次模拟中恰好最有利的动作差。}
$$

技术上，同一状态重复加载同一随机数状态只会重演同一条轨迹，不能冒充独立重复；新增未来扰动也必须单独声明，不能偷偷改变原正式实验的需求与路由协议。

**如果条件平均收益可以重复，模型才有值得学习的目标；如果只有事后挑选的单次收益很大，再复杂的 gate 也可能追逐噪声。**

### 第三项诊断：当前 rigid 表示是否遗漏了决定迁移方向的信息？

现有 `CAUSAL_RIGID_RANKING_PARENTS` 已包含队列、下游占用、压力、切换、`clearance_fraction` 和相位重叠等信息，因此“再加 downstream occupancy”并不是新解决方案。

更值得检验的假设是：

> **相似的聚合压力和队列状态，在不同通行权、接收车道冲突、执行器阶段及邻居放行条件下，可能对应不同的实际服务响应。**

具体检查 protected/yielding movement、共享接收车道、邻接路口的当前相位与剩余执行约束，是否解释了 source 效果的符号翻转。这里只能使用决策前可获得的信息，不能使用未来真实到达流、未来拥堵结果或测试标签。

这不是宣称这些因素已经被证明是负迁移原因，而是一个**可以被实验推翻、并能指导表示修改的具体假设**。

## 三、新方法应怎么改：迁移“条件化的机制先验”，而不是整个城市的残差

你的 mechanism-specific shrinkage 思路是合理的，但需要真正落到模型结构上。

### 1. V148 的“机制门控”实际上仍然是一个标量门控

V148 对五类机制分别计算预测误差改善，再把五个 trust 的均值当作 source mass：

$$
\widehat q_s
=
\widehat q_{\mathrm{TO}}
+
\alpha_s
\left(
\widehat q_{\mathrm{source}}
-
\widehat q_{\mathrm{TO}}
\right).
$$

机制预测本身不进入动作评分，而只是控制整个 source residual 的混合比例。随后，该 source 还要通过其他五个目标城市上的历史安全条件。

因此，V148 没有真正实现：

> “source A 的放行机制可以借，spillback 机制不借。”

它实现的是：

> “综合五种预测表现，决定把 source A 的整段 residual 借多少。”

这两者差别很大。一个 source 可能改善多个与动作排序关系不大的预测量，却损害真正决定相位选择的机制；反过来也可能成立。

### 2. 建议的迁移对象：结构化动作差中的机制参数

保留动作对比的主线，不建议直接复活完整 MC-WM 控制器。新候选可以将动作差表示成少量机制项：

$$
d_t(x,a,b)
=
\sum_m
\left[
f_{\theta_{t,m}}(x,a)
-
f_{\theta_{t,m}}(x,b)
\right].
$$

source 为其中部分参数提供先验，而不是直接成为整个目标模型的替代品：

$$
\widehat\theta_t
=
\arg\min_\theta
\left\{
\mathcal L_T(\theta;D_T^{(B)})
+
\mathcal R_0(\theta)
+
\sum_{s,m}
\lambda_{s,m}\,
\|\theta_m-\mu_{s,m}\|_{W_{s,m}}^2
\right\}.
$$

其中，\(\mu_{s,m}\) 是 source 的机制先验，\(W_{s,m}\) 表达可信度，\(\lambda_{s,m}\) 控制借用强度；**所有 \(\lambda=0\) 时，必须精确恢复同架构 target-only**。

这里有两个关键设计要求：

**第一，先验需要包含“可迁移差异”的不确定性。** source 数据很多，只能说明 source 内部估计更精确，不能说明它更适合 target。不能因为 source 样本多，就把错误先验做得异常强。

**第二，target 数据增加时，不应强迫保持 source 权重。** 若 source 仍有系统偏差，让 target 数据逐渐压过先验是正确行为，不是迁移失败。

而且，仓库的 V128/V129 已经说明：避免 target residual 抵消 source prior，并不自动解决 held-out 识别问题。因此，这里的重点必须是**更合适的机制对象和可辨识的条件收益**，不是简单把 source 改名为 prior。

### 3. utility gate 要预测“边际收益”，但不要一开始做成大模型

对于固定的 target-only 和一个候选 source 机制，监督标签可以写为：

$$
Y_{s,m}
=
R(\pi_{\mathrm{TO}})
-
R(\pi_{s,m}).
$$

在相同状态、相同候选集合和相同成本定义下，regret 中的最优动作成本会相消：

$$
Y_{s,m}
=
C(a_{\mathrm{TO}})
-
C(a_{s,m}).
$$

这意味着，门控真正要学的是：

> **在这个条件下，加入这一块 source 信息，是否改变了动作，并且改变是否有益？**

不是 source 的 next-state MSE，也不是 source 与 target 的总体相似度。

不过，**七个城市不足以支撑高自由度的 source–target–机制深度门控**。我建议第一版只保留少数经诊断确认的机制和低复杂度条件模型，先测试单 source、单机制的增量，再扩展组合。多个单独有益的修正组合起来，不一定仍然有益。

所有 utility 训练记录必须来自严格的 out-of-fold 候选模型；held-out 城市不得以 target、source 或任何统计预处理角色进入该折训练。**42 个 source–target 组合也不是 42 个独立城市样本。**

## 四、PhasePressure 问题：可以研究安全偏离，但必须更换“收益证据”

你的“PhasePressure + CFCMT 安全偏离”方向合理，**但它是设计框架，不是解决办法本身**。项目已有保守 intervention gate 全部回退的记录，也有看起来有利的执行层方案在新种子确认中收益几乎消失的记录。

下一代偏离规则，最好围绕下面这个量：

$$
G(x,a)
=
Q^{\pi_P}(x,\pi_P(x))
-
Q^{\pi_P}(x,a),
$$

其中 \(\pi_P\) 为 PhasePressure，\(Q^{\pi_P}(x,a)\) 表示：**当前执行动作 \(a\)，之后遵循明确的基线延续策略时的长期成本**。

只有当可信的收益下界为正，才允许偏离：

$$
\widehat G(x,a)-\varepsilon(x,a)>\tau.
$$

真正困难的是 \(\varepsilon\) 是否覆盖了相关误差。它不能只是模型集成的标准差，还要处理有限预测时域、执行器切换、状态分布变化和相邻路口共同动作的影响。

尤其要避免两个推理跳跃：

**局部一步改善，不等于全网长期改善。** 标签中应包含实际 yellow/all-red、最短绿灯等执行过程，并检验下游排队传播和未完成车辆，而不是只比较理想化的相位动作。

**多个路口各自“安全”，不等于同时改变后安全。** 单路口干预标签不能直接支持同时全网干预的保证；必须对联合动作或显式干扰条件进行验证。

这种“高不确定性时保留基线”的思想已有 Safe Policy Improvement 文献基础；你的创新不能仅仅是添加 fallback，而应当在于**交通机制下如何得到可用、可校准的收益证据**。([Proceedings of Machine Learning Research][1])

我的建议是：**先把 source contribution 与压力超越拆成两个研究阶段。** 第一阶段证明相同架构、相同预算下 source 有增量价值；第二阶段再检验它能否帮助辨认 PhasePressure 的有益偏离。两者都保留压力结果，但不要把两个失败来源混在一次实验里。

## 五、Boston：修复路线明确，但“G → g”不一定是完整修复

Boston v11 的记录已经把问题定位到 `joinedS_514` 的 link 0 与 uncontrolled major movement 共用接收车道。它属于 package admission 缺陷，而不是 CFCMT 性能证据。

这里我同意你的判断：**不要继续只修最后一次碰撞的位置。** 应把已经暴露的错误类别编成全网审计规则。

建议审计至少覆盖三类关系：受保护信号流与 uncontrolled major 的共享接收车道冲突；多个 uncontrolled major 的优先权冲突；junction type、connection state 与内部连接/清空过程的不一致。每个候选问题输出明确的 connection、TLS/link/phase、下游车道、foe/response 和修改理由，而不是直接批量改 XML。

尤其需要补充一个重要细节：

**SUMO 中，小写 `g` 的正确让行依赖底层 right-of-way 关系。官方文档明确指出，引入新的 `g/G` 关系时，需要通过 `netconvert` 更新相应通行权规则，不能只假定字符修改就足够。** 同时，joined TLS 的 link index 与各 junction 内部索引不能混用。([日食SUMO][2])

因此，对于 phase 6/link 0：

> `G → g` 是合理候选修复，但必须同时确认它真的会向冲突主流让行；如果 foe/response 本身不正确，就需要把相应修改纳入新 package 的声明与审计。

随后仍按 **static → complete routes → trigger windows → full-day admission** 运行。还要防止“靠长期不放车实现零碰撞”：通行能力、完成情况和完整需求核对必须继续保留。

**我对修复已定位的冲突类别有较高把握，但不能据此保证 v12 不会再暴露其他缺陷。** Boston 修复可以与七城科研诊断并行，不应成为所有方法工作的串行阻塞点。它即使通过，也不改变 V149 永久关闭的决定。

## 六、下一轮实验怎样安排，才能真正回答问题

我建议按下面的顺序收敛，而不是再连续启动一串不同 gate。

| 阶段       | 必须产出的结果                                             | 继续条件                |
| -------- | --------------------------------------------------- | ------------------- |
| 收益可重复性诊断 | 固定选择规则在新增开发数据上的收益；条件平均收益与随机波动分解                     | 发现可以重复的收益结构         |
| 表示诊断     | 哪些部署可观测信息能解释 source/动作收益翻转                          | 新信息确实改善 held-out 识别 |
| 最小机制迁移模型 | 同架构 target-only、真实 source prior、matched placebo 的对比 | 收益来自 source，而不只是新表示 |
| 闭环验证     | 独立开发种子上的完整运行、尾部损失、完成率与事故记录                          | 不只是离线 regret 改善     |
| 冻结与外部确认  | 全新协议、完整数据角色清单、未参与方法选择的城市                            | 一次性按预设标准判断          |

这里有几个需要预先固定的细节。

**预算不能只写 B25。** 应明确 B 是状态组、动作组还是轨迹；每组多少反事实动作、每个动作多长 rollout、门控是否额外使用 target 标签。target-only 必须获得匹配的信息预算和合理使用这些信息的机会。

**B=0 必须单独定义。** 没有 target 标签时，并不存在普通意义上的“拟合后的 target-only 模型”；应声明对应的 source-free physics/rigid 基线。B=1 也不能沿用五折交叉验证。预算曲线可以保留，但应预设主预算或主曲线统计量，不能结果出来后挑最有利的点。

**至少三个新城市是合理的最低扩展，不是充分统计保证。** 举例说，只有三个独立城市，即便三个效果都为正，简单单侧符号检验在零假设下的概率仍是 \(1/8=0.125\)。因此，应根据城市间效应异质性和希望识别的最小收益决定样本量，而不是把“三个城市”当作自动通过线。

**新增状态表示后必须重新隔离结构收益与 source 收益。** 最重要的比较是：

$$
\text{新表示 + source}
\quad\text{vs}\quad
\text{同一新表示 + target-only}.
$$

否则，很容易再次把“模型结构更好了”误写成“跨城市迁移成功了”。

## 七、外部效度和发布：能补，但不要与算法问题混为一谈

同协议基线应优先完成一个最接近你信息设定的方法，而不是先追求名称齐全。状态、可执行动作、target 信息预算、调参机会和闭环成本都要对齐；项目讨论已经明确指出，直接拿 CrossLight/MetaLight 等原论文数字来横向排名不能解决这个问题。

真实世界效果仍需要相应实证。数字孪生校准能够检验部分 simulator mismatch，但**校准本身也不等于已经验证真实干预效果**。没有这类证据时，保留 simulator-local 的结论即可，不必为了扩大表述而模糊边界。

发布方面，你提供的 `40 tracked / 1399 untracked` 是本地工作树信息，我不能从远端确认它现在是否仍成立。能确认的是，当前 Data Availability 仍将持久化公开归档与 DOI 写成待完成事项。

建议区分轻量代码 release 和证据归档：前者放代码、配置、canonical 表格、小型结果和重建脚本；后者保存可授权分发的必要网络输入、模型和原始运行证据，并用 manifest/hash 关联。**不把巨量中间结果放入 Git，并不意味着把复核结论需要的证据也删掉。**

## 最终判断

**Boston 是有明确路径的工程修复；跨城市收益是值得继续推进的科研问题；普遍击败 PhasePressure 则不应成为当前必须兑现的承诺。**

我会把你原来的研究优先级调整为：

> **Boston 并行系统修复；主研究先验证收益的可重复性和可辨识性，再构造机制级 source prior 与条件 utility，随后做闭环验证，最后冻结并进入新城市。**

这个项目最有潜力的下一步，不是“再多一个保守 gate”，而是建立并验证下面这个主张：

> **跨城市可迁移的不是整座城市的预测残差，而是在明确运行条件下、对动作选择有用且能够被识别的机制信息；超出这些条件时，模型应拒绝迁移。**

“模型应服务于决策，而不必完整预测环境”已有 value-equivalence 等研究基础。因此，真正可能成为你论文贡献的，是**找到这些条件、证明它们具有事前预测力，并在未参与方法选择的城市中验证 source 的增量价值**，而不是只把已有模块组合起来。
